## 1. 문서 목적

이 문서는 SCAN 2026 참가를 검토하면서 논의한 내용을 하나의 기준으로 정리한다. 현재 단계의 목적은 구현을 시작하는 것이 아니라 다음 순서를 합의하는 것이다.

1. 대회의 성격과 확정 정보를 파악한다.
2. 출제 가능성이 있는 문제를 충분히 도출한다.
3. 각 예상문제의 수동 풀이 과정을 설계한다.
4. 반복되는 분석 작업을 식별한다.
5. 반복 작업을 빠르고 정확하게 수행할 도구를 정의한다.
6. 문제 해결 기여도에 따라 구현 우선순위와 기술을 결정한다.

이 문서는 공식 정보, 과거 사례, 우리의 예상, 우리의 결정을 구분한다. 아직 공개되지 않은 규정을 추측으로 확정하지 않는다.

## 3. 대회 개요

### 3.1 확정 사실

- SCAN은 Secure Crypto-Asset Network의 약자이며 디지털자산 추적 역량을 겨루는 실전형 경진대회다.
- 일반적인 아이디어·제품 개발형 해커톤이 아니라 주최 측이 제시하는 문제를 제한 시간 안에 해결하는 CTF 성격의 대회다.
- 평가는 온체인 데이터 분석, 트랜잭션 흐름 추적, 지갑 행동 패턴 식별, 블록체인 포렌식 사고력 등을 중심으로 한다.
- 팀당 최대 4명까지 참가할 수 있다.
- 디지털자산 추적과 블록체인 보안에 관심이 있다면 누구나 참가 신청이 가능하다고 안내되어 있다.
- 사전등록은 2026년 7월 27일 12:00 KST에 시작될 예정이다.
- 온라인 예선은 2026년 8월 2일 09:00 KST부터 24시간 동안 진행될 예정이다.
- 예선 상위 20개 팀이 2026년 9월 28일 서울 모나코스페이스에서 열리는 본선에 진출한다.
- 컨퍼런스와 시상식은 2026년 10월 1일 서울 워커힐호텔 워커홀에서 열린다.
- 총상금은 2 BTC로 안내되어 있다.
- 주최사는 디애셋이며 CTF 파트너는 Chainalysis다.

### 3.2 확인이 필요한 사항

- 개인 참가 가능 여부와 최소 팀 인원
- 팀 생성·합류·변경 방법 및 마감 시각
- 문제 및 정답 제출 플랫폼
- 점수 산정, 동점 처리, 힌트와 감점 규칙
- 외부 API, 자동화 스크립트, AI, 상용 분석 서비스의 허용 범위
- 팀 외부 인원과의 협업 제한
- 본선 진출자의 현장 참석 의무와 신원 확인 방식
- 지원 언어 및 정답 제출 형식
- 분석 대상 체인과 사전 제공 데이터
- 공식 상금표의 1~18위 합계 1.979 BTC와 총상금 2 BTC 간 차이

세부 규정이 공개되면 이 문서를 갱신하고, 준비 중인 도구가 규정을 위반하지 않는지 다시 확인해야 한다.

## 4. 과거 대회에서 확인되는 문제 성격

SCAN 2024 온라인 예선은 24시간 동안 진행되었고 46개국 630팀, 1,177명이 참가했다. 당시 문제는 다음 범위를 포함했다.

- 블록체인 기본 원리
- 지갑 구조 분석
- 트랜잭션 구조 분석
- 가상자산 범죄자금 추적

이 내용은 2026년 문제를 그대로 예고하는 공식 출제 범위가 아니다. 다만 예상문제의 기초 범위를 설정할 수 있는 가장 가까운 과거 근거다.

## 5. 일반적인 아이디어형 해커톤과의 차이

| 구분 | 아이디어·개발형 해커톤 | SCAN형 추적 CTF |
|:---|:---|:---|
| 시작점 | 참가자가 문제와 아이디어를 정의 | 주최 측이 문제와 단서를 제시 |
| 주요 산출물 | 서비스, 프로토타입, 발표자료 | 정답, 분석 결과, 온체인 증거 |
| 핵심 역량 | 기획, 개발, 디자인, 발표 | 데이터 분석, 추적, 포렌식, 문제 해결 |
| 준비 방향 | 아이디어와 구현 범위 구상 | 예상문제 풀이와 반복 분석 자동화 |
| 대회 중 작업 | 제품 제작 및 발표 준비 | 문제 분배, 분석, 검증, 정답 제출 |

따라서 현재 준비의 중심은 서비스 아이디어 발굴이 아니라 예상문제와 분석 워크플로 설계다.

## 6. 우리의 목표

### 6.1 현재 결정

- SCAN 2026 참가를 구체적으로 검토한다.
- 구현에 앞서 예상문제 은행을 만든다.
- 예상문제의 수동 풀이 절차를 먼저 설계한다.
- 여러 문제에서 반복되는 작업만 도구화한다.
- 속도뿐 아니라 결과의 정확성, 재현성, 증거 보존을 중시한다.
- 도구는 자동 정답기가 아니라 사람의 판단을 돕는 반자동 분석 워크벤치를 지향한다.
- 기술 스택은 예상문제와 기능 요구사항을 도출한 후 결정한다.

### 6.2 미결정

- 참가 확정 여부
- 개인 또는 팀 참가 방식
- 목표 수준: 예선 완주, 본선 진출 또는 수상
- 지원할 블록체인 범위
- 사용할 공개·유료 데이터 서비스
- 최종 기술 스택
- 도구 구현 범위와 일정

## 7. 핵심 준비 전략

### 7.1 문제 우선 접근

준비 순서는 다음과 같이 고정한다.

1. 예상문제를 폭넓게 작성한다.
2. 문제마다 주어진 단서와 요구 정답을 정의한다.
3. 도구 없이 해결한다고 가정하고 수동 풀이 단계를 작성한다.
4. 필요한 데이터와 외부 정보원을 식별한다.
5. 수동 풀이에서 반복되는 작업을 기능 단위로 추출한다.
6. 기능의 문제 적용 빈도와 시간 절감 효과를 계산한다.
7. 공통 사용 빈도가 높은 기능부터 도구 후보로 선정한다.
8. 기술 스택과 구현 난이도를 평가한다.
9. 구현 여부와 우선순위를 결정한다.
10. 과거 사건이나 자체 제작 문제로 정확성을 검증한다.

### 7.2 피해야 할 접근

- 예상문제 분석 없이 특정 기술이나 프레임워크부터 확정하는 것
- 사용 가능성이 불분명한 기능을 먼저 만드는 것
- 외부 서비스 한 곳의 주소 라벨을 사실로 간주하는 것
- 그래프의 시각적 연결만으로 동일 주체라고 단정하는 것
- 자동 분석 결과에 근거 트랜잭션을 남기지 않는 것
- API 장애나 호출 제한을 고려하지 않는 것
- 대회 규정 확인 전에 자동화 도구 사용이 허용된다고 가정하는 것

## 8. 예상문제 분류 체계

예상문제 은행은 아래 분류를 최소 범위로 삼는다.

### 8.1 블록체인 기초

- 주소, 블록, 트랜잭션 해시 식별
- 수수료, 논스, 입력 데이터 해석
- 특정 시점의 잔액과 자산 보유량 계산

### 8.2 EVM 네이티브 자산과 토큰

- 네이티브 코인 이동
- ERC-20 전송
- NFT 이동
- 내부 호출과 컨트랙트 생성
- 이벤트 로그 기반 실제 자산 흐름 복원

### 8.3 자금 흐름

- 단일 경로 추적
- 여러 단계의 자금 이동
- 다수 주소로의 분산
- 여러 주소에서의 재병합
- 순환 거래와 셀프 전송
- 특정 금액 또는 특정 피해금의 추적

### 8.4 서비스 식별

- 중앙화 거래소 입금
- DEX 스왑
- 브리지와 크로스체인 이동
- 믹서 및 프라이버시 서비스
- 대출, 스테이킹, 파생상품 프로토콜

### 8.5 행위자와 지갑 관계

- 공통 자금 출처
- 공통 수수료 지급자
- 공통 목적지
- 거래 시각과 행동 패턴
- 동일 컨트랙트 호출 순서
- 동일 주체가 통제할 가능성이 있는 주소 집합

### 8.6 범죄·사건 유형

- 피싱
- 지갑 탈취
- 스마트컨트랙트 익스플로잇
- 러그풀
- 자금세탁
- 랜섬웨어
- 제재 대상 주소와의 연관성

### 8.7 Bitcoin

- UTXO 흐름
- 입력 주소 공동소유 휴리스틱
- 잔돈 주소 추정
- CoinJoin 가능성 식별
- 다단계 BTC 이동

### 8.8 OSINT 결합

- 주소와 공개 사건 보고서 연결
- 프로젝트·도메인·SNS·GitHub 정보 연결
- 공개 제재 목록과 보안업체 보고서 검색
- 주소 라벨의 출처와 신뢰도 비교

### 8.9 종합 문제

- 여러 체인과 여러 자산이 섞인 자금 이동
- 스왑·브리지·거래소가 연속된 경로
- 불완전한 단서를 바탕으로 한 사건 재구성
- 온체인 데이터와 OSINT를 함께 사용해야 하는 문제

## 9. 예상문제 표준 작성 형식

각 예상문제는 다음 항목을 포함한다.

```text
문제 ID:
문제 분류:
난이도:

문제 설명:
주어진 단서:
요구되는 정답:

수동 풀이 단계:
필요한 온체인 데이터:
필요한 오프체인 데이터:
사용 가능한 외부 정보원:

반복 작업:
자동화 가능한 부분:
사람이 판단해야 하는 부분:

정답의 증거:
오답 가능성과 예외:
필요한 도구 기능:
```

### 9.1 예상문제 예시

```text
문제 ID: FLOW-EVM-001
문제 분류: EVM / 자금 흐름 / 거래소 유입
난이도: 중

문제 설명:
피싱 주소 A에서 빠져나간 50 ETH의 최종 도착지를 찾아라.

주어진 단서:
- 피해 주소 A
- 피해 발생 시각
- 피해 금액

요구되는 정답:
- 최종 도착 서비스 또는 주소
- 실제 이동 금액
- 판단 근거 트랜잭션

수동 풀이 단계:
1. A의 출금 거래를 수집한다.
2. 시간과 금액 조건에 맞는 최초 거래를 식별한다.
3. 다음 주소의 후속 출금을 추적한다.
4. 스왑과 브리지 사용 여부를 확인한다.
5. 최종 거래소 유입 가능성을 검증한다.
6. 각 단계의 트랜잭션 해시를 정리한다.

자동화 가능한 부분:
- 거래 수집
- 시간·금액 필터
- N홉 경로 생성
- 알려진 서비스 주소 라벨링
- 경로 시각화
- 증거 목록 생성

사람이 판단해야 하는 부분:
- 라벨이 없는 거래소 입금주소의 귀속
- 여러 갈래 중 실제 피해금에 해당하는 경로
- 휴리스틱 결과의 신뢰도
```

- 내부 트랜잭션과 이벤트 로그 수집

- 복수 체인의 공통 데이터 형식 변환
- API 결과 캐시와 중단 후 재개

### 11.2 자금 추적

- 시간·금액·자산 필터
- N홉 전방·후방 추적
- 분산과 병합 탐지
- 공통 출발지·도착지 계산
- 순환 경로 제거
- 특정 피해금의 이동 후보 계산

### 11.3 주소 및 서비스 라벨링

- 거래소, DEX, 브리지, 믹서 식별
- 공개 제재·범죄 관련 주소 조회
- 라벨 출처와 신뢰도 기록
- 서로 다른 라벨 소스의 충돌 표시

### 11.4 프로토콜 해석

- ERC-20 이벤트 해석
- DEX 스왑 전후 자산 계산
- 주요 브리지의 출발·도착 거래 연결
- 컨트랙트 호출과 이벤트 요약

### 11.5 시각화

- 주소를 노드, 자금 이동을 엣지로 표현
- 체인, 자산, 서비스, 시간, 금액 필터
- 출발지와 핵심 경로 강조
- 그래프와 원본 트랜잭션 간 이동

### 11.6 OSINT

- 주소 문자열 기반 공개정보 검색
- 사건 보고서와 제재 목록 연결
- 발견한 근거 URL과 인용 내용 저장

### 11.7 증거와 보고서

- 주소, 금액, 자산, 시각, 트랜잭션 해시 기록
- 확인된 사실과 휴리스틱 추정 분리
- CSV, JSON 및 사람이 읽는 보고서 출력
- 분석 데이터 출처와 생성 시각 기록

## 12. 자동화 원칙

### 12.1 자동화하기 적합한 부분

- API를 통한 반복 데이터 수집
- 데이터 정렬, 필터링, 합계 계산
- 주소 간 경로 탐색
- 알려진 주소 라벨 조회
- 후보 경로와 관계 그래프 생성
- 근거 트랜잭션 목록 작성

### 12.2 사람이 판단해야 하는 부분

- 라벨이 없는 주소의 실제 소유자
- 동일 주체가 통제하는 주소인지 여부
- 믹서 또는 CoinJoin 이후의 불확실한 연결
- 여러 후보 경로 중 사건과 관련된 경로
- 새로운 브리지나 컨트랙트의 의미
- 온체인 증거와 사건 맥락을 결합한 최종 결론

도구의 결과는 사실, 휴리스틱 추정, 외부 라벨을 구분해서 표시해야 한다. 휴리스틱 결과를 확정 사실로 출력해서는 안 된다.

## 13. 기술 선택 원칙

기술 스택은 아직 결정하지 않는다. 다음 기준으로 후보를 비교한다.

- 예상문제 해결에 필요한 라이브러리와 데이터 접근성
- 구현 및 수정 속도
- 대량 거래 데이터 처리 성능
- EVM과 Bitcoin 지원 수준
- 그래프 분석 및 시각화 지원
- CLI, 노트북, 웹 UI 중 적합한 사용 방식
- 팀원의 숙련도
- 오프라인 분석과 캐시 지원
- 배포 없이 로컬에서 실행할 수 있는지 여부
- 보안과 API 키 관리

### 13.1 Python이 후보로 언급된 이유

Python은 데이터 수집, 테이블 처리, 그래프 분석, 자동화와 실험에 적합하기 때문에 초기 후보로 언급되었다. 그러나 이는 최종 결정이 아니다.

### 13.2 비교 대상

| 기술 | 강점 | 고려사항 |
|:---|:---|:---|
| Python | 데이터 분석, 자동화, 그래프 계산, 빠른 실험 | 복잡한 인터랙티브 UI 구성은 별도 고려 필요 |
| TypeScript/Node.js | EVM 생태계, 웹 UI, 실시간 상호작용 | 대량 분석 작업의 구현 복잡도 검토 필요 |
| Go/Rust | 성능, 병렬 수집, 단일 바이너리 | 제한된 준비 기간에서 개발 속도 부담 |
| SQL/DuckDB | 대량 조회, 필터, 집계 | 단독으로 전체 추적 워크플로를 구성하기 어려움 |

필요하다면 분석 엔진, 저장소, 시각화를 서로 다른 기술로 구성할 수 있다. 다만 예상문제가 정리되기 전에 혼합 기술 구조를 확정하지 않는다.

## 14. 위험과 제약

| 위험 | 영향 | 대응 방향 |
|:---|:---|:---|
| 2026 세부 규정 미공개 | 준비한 도구를 사용할 수 없을 수 있음 | 등록 시작 후 규정 우선 검토 |
| API 호출 제한 또는 장애 | 데이터 수집 중단 | 캐시, 재시도, 복수 데이터 소스 검토 |
| 잘못된 주소 라벨 | 오답 가능성 | 라벨 출처와 신뢰도 표시, 교차검증 |
| 상용 서비스 접근 제한 | 팀원별 결과 차이 | 공개 데이터 기반 기본 경로 확보 |
| 체인별 데이터 구조 차이 | 정규화 오류 | 체인별 검증 사례와 원본 데이터 보존 |
| 믹서·브리지의 불확실성 | 경로를 과도하게 단정 | 후보와 확정 사실 분리 |
| 구현에 시간 과다 사용 | 문제풀이 연습 부족 | 문제 적용 빈도에 따른 기능 우선순위 |
| 자동화 과신 | 맥락을 놓치거나 잘못된 결론 | 사람이 검증하는 반자동 구조 유지 |
